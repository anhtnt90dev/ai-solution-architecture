# Code Of Conduct

This project is intended to be a professional learning space for AI engineers, solution architects, and contributors.

## Expected Behavior

- Be respectful and direct.
- Critique ideas, artifacts, diagrams, and reasoning, not people.
- Prefer evidence, examples, and concrete trade-offs.
- Assume good intent, but correct unclear or unsafe guidance.
- Keep discussions relevant to AI solution architecture, production engineering, and learning quality.

## Unacceptable Behavior

- Harassment, insults, intimidation, or discriminatory language.
- Publishing private data, secrets, or confidential architecture material.
- Spam, self-promotion without educational value, or misleading claims.
- Unsafe technical guidance presented as production-ready without caveats.

## Enforcement

Maintainers may edit, hide, or remove content that violates this code of conduct. Repeated or severe violations can lead to blocked participation.

Report issues through GitHub Issues or by contacting the repository owner.

## Review Culture

This repository invites technical disagreement. A useful contribution can challenge a diagram, reject a runtime choice, question a RAG pattern, or point out that a checklist misses an important production risk. The expected standard is that criticism should include evidence or a concrete example. Comments such as "this tool is bad" or "this architecture is wrong" are not useful unless they explain the constraint, failure mode, or trade-off.

When reviewing contributions, focus on whether the material helps a senior engineer or solution architect make a better decision. Good reviews ask whether the document separates product workflow from model runtime, whether retrieval access control is explicit, whether evaluation is measurable, whether tool execution is governed, and whether operations teams can observe the system after launch.

## Language And Translation

The project is bilingual. Contributors may write in English or Vietnamese. Translation feedback should preserve technical meaning and avoid changing architecture claims without explanation. When a Vietnamese phrase needs a precise English technical term, keep the term if it improves clarity for practitioners. When English content is translated into Vietnamese, use natural Vietnamese with full accents and avoid temporary unaccented draft wording.

## Maintainer Actions

Maintainers may request edits, close low-signal issues, label discussions by domain, or ask contributors to move broad debates into a more focused proposal. These actions are meant to keep the repository useful as a knowledge system. If a moderation decision seems unclear, ask for the technical or conduct reason directly and keep the discussion scoped to the artifact being reviewed.
